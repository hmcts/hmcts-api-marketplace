Data Governance Standards

Legal and regulatory obligations for all participants in the HMCTS API Marketplace.

Contents

  1. Legal framework
  2. Data classification
  3. Data sharing agreements
  4. Minimisation and retention
  5. Access control
  6. Audit and monitoring
  7. Data breaches
  8. Cross-border transfers
  9. Accountability
  10. Decommissioning
These standards apply to all consumers and producers. Based on UK GDPR, DPA 2018 and HMG Security Classification policy. Role-specific obligations are noted throughout.

1. Legal framework

All participants must comply with:

UK GDPR and Data Protection Act 2018
Personal data must be processed lawfully with a documented legal basis. Producers must record this in the API spec. Consumers must not use data beyond the stated purpose.
Government Security Classifications policy
Official-Sensitive data requires enhanced controls. All APIs must declare their classification in the marketplace.
Computer Misuse Act 1990
Unauthorised access is a criminal offence. Credentials must not be shared or misused.
Freedom of Information Act 2000
Some API-accessible data may be subject to FOI requests. All participants should be aware of their obligations.
Public Records Act 1958
Court records may carry public record obligations. Producers must check these before exposing court data through an API.

2. Data classification

Every API must declare a classification. Consumers must not downgrade data once received.

ClassificationEligible?Producer obligationsConsumer obligations
OfficialYesStandard data protection controls. Declare in OpenAPI spec.Handle per your organisation’s information security policy.
Official-SensitiveWith conditionsFormal DSA required before any access granted. Verify enhanced controls at consumer.Formal DSA required. Enhanced access controls and audit logging. Do not downgrade.
Secret / Top SecretNoNot eligible for listing on the marketplace.

3. Data sharing agreements

!WarningNo personal data API may be accessed without a signed DPA or DSA in place.

Producers must:

  • Confirm a DPA or DSA is in place before approving access to any personal data API
  • Record the legal basis for the data sharing arrangement
  • Notify their DPO of any new data sharing arrangements

Consumers must:

  • Ensure their legal team has reviewed the arrangement before submitting a request
  • Not use data beyond the stated purposes
  • Report any change in use case to the API owner before proceeding

4. Data minimisation and retention

Producers must:

  • Expose only the minimum data fields necessary
  • Review exposed fields when a consumer’s access is revoked
  • Not expose internal identifiers or debug data in responses

Consumers must:

  • Only request access to fields actually needed
  • Not cache responses beyond the time needed
  • Define a retention period and delete data when no longer required

5. Access control and authentication

OAuth 2.0 with JWT bearer tokens is mandatory for all marketplace APIs.

All participants:

  • Scope tokens to minimum permissions required
  • Never share credentials between services, teams or individuals
  • Report and revoke compromised credentials immediately

Consumers additionally:

  • Use separate credentials per consuming service
  • Never hard-code tokens in source code
  • Implement token rotation and expiry handling

Producers additionally:

  • Verify consumer identity before approving access
  • Be able to revoke access immediately
  • Maintain an audit log of access grants

6. Audit and monitoring

Producers must:

  • Log all API calls: timestamp, consumer ID, endpoint and response code
  • Retain logs for a minimum of 12 months
  • Make logs available to the marketplace or HMCTS security team on request

Consumers must not:

  • Attempt to circumvent rate limiting, access controls or monitoring
  • Use the API to enumerate or harvest data beyond the stated use case

7. Data breaches and incident management

!WarningAny suspected breach must be reported to the HMCTS DPO within 72 hours (UK GDPR Article 33).

All participants:

  • Do not conceal or delay breach notification
  • Preserve logs and evidence for investigation

Producers additionally:

  • Maintain an incident response plan covering API-related breaches
  • Notify affected consumers as part of incident response

Consumers additionally:

  • Have a process to notify end users if personal data is compromised
To report a breach contact the HMCTS marketplace team immediately.

8. Cross-border data transfers

  • API responses must not be routed through or stored outside the UK or EEA without prior written DPO approval
  • Cloud infrastructure processing API responses must be documented in your ROPA
  • Transfers to third countries must comply with UK GDPR Chapter V

9. Accountability and governance roles

RoleResponsibility
Data ControllerHMCTS — responsible for lawfulness of processing across the marketplace
Data ProcessorConsumer organisations processing personal data on behalf of HMCTS
API Owner (Producer)Accountable for accuracy, security and lawfulness of data exposed through their API
Marketplace teamResponsible for onboarding governance, standards enforcement and access audit
DPOMust be consulted on new data sharing arrangements. Must be notified of breaches within 72 hours.

10. Decommissioning and offboarding

Consumers must:

  • Revoke credentials and notify the API owner when decommissioning
  • Delete all API-derived data or return to the data controller
  • Provide a data deletion certificate on request

Producers must:

  • Give consumers at least 30 days’ notice before retiring an API
  • Ensure all consumers have migrated before retirement
  • Explicitly revoke all active credentials at retirement

Questions? Contact the marketplace team or consult your DPO.

API Producer Standards

Standards and requirements for listing an API on the HMCTS API Marketplace.

Contents

  1. Technical requirements
  2. Eligibility criteria
  3. Specification quality
  4. Onboarding process
  5. Ongoing responsibilities
  6. Data governance
These standards are based on the HMCTS RESTful API Standards and the AMP Catalogue onboarding process. If you have questions, contact the marketplace team.

1. Technical requirements

Your API must meet the following technical requirements before it can be listed on the marketplace.

OpenAPI 3.x specification

Your API must have a valid OpenAPI 3.x specification file at the following path in your repository:

src/main/resources/openapi/openapi-spec.yml

The specification must include:

  • info.title — a clear, human-readable API name
  • info.description — a plain-English summary of what the API does
  • info.version — the current version (stamped automatically from the GitHub release tag)
  • At least one path with at least one operation

Servers block

The servers block must follow the standard HMCTS pattern. Do not use SwaggerHub virtual server URLs.

servers:
  - description: <API title>
    url: https://<repo-name>.net/{version}
    variables:
      version:
        default: <info.version>
! WarningDo not hand-bump the version. It is stamped automatically when you cut a GitHub release.

Spectral linting

Your specification must pass the standard Spectral OAS3 ruleset with no errors. Run locally before submitting:

spectral lint src/main/resources/openapi/openapi-spec.yml

GitHub Actions workflow

Add the following file to your repository to publish documentation automatically on each release:

.github/workflows/publish-api-docs.yml

This triggers the shared amp-catalog workflow pinned to @v1. See the amp-catalog repository for the full workflow template.

2. Eligibility criteria

! WarningOnly external APIs may be listed. Internal APIs must not be exposed publicly via GitHub Pages.
API type Eligible? Notes
External, documentation-only Eligible Spec is world-readable via GitHub Pages
External, with mock execution Eligible Try-It disabled; documentation only in marketplace
Internal / developers only Not eligible Must wait for the APIM Developer Portal

Your API repository must also be public on GitHub. The documentation site is served via GitHub Pages and must return HTTP 200 at https://hmcts.github.io/<repo-name>/ before your listing goes live.

3. Specification quality

Your OpenAPI specification should meet the following quality standards. These ensure a good experience for consumers browsing the marketplace and directly power the information shown on each API’s detail page.

Title
Clear, human-readable name — not the repository slug
Plain-English description
A consumer-focused summary of what the API does, who it is for, and what data it returns. This is shown directly in the marketplace under “What does this API do?”
Contact email
A real team inbox — not Nagashankar.Ponnaganti@HMCTS.NET
Endpoint summaries
Every operation must have a summary and a description
Schema definitions
All request and response bodies defined as named schemas in components/schemas with property descriptions
Security scheme
Authentication method declared (e.g. bearerAuth) and applied to all protected operations
Error responses
400, 401, 404 and 500 responses documented for each operation

4. Onboarding process

  1. Ensure your API repository is public on GitHub under the HMCTS organisation
  2. Add the publish-api-docs.yml workflow to .github/workflows/ and raise a PR
  3. Once merged, trigger the workflow manually or cut a GitHub release — the version is stamped from the release tag
  4. Confirm the Swagger UI documentation site is live at https://hmcts.github.io/<repo-name>/
  5. Register as a Producer and submit your API via the Publish API form in your producer dashboard
  6. The marketplace team will review and approve your submission within 2 working days
  7. Once approved, your API will appear in the catalogue and be automatically kept in sync with your specification
Ready to publish? Sign in or register and go to the Publish API section of your producer dashboard.

5. Ongoing responsibilities

Once your API is listed, you are responsible for:

Keeping the spec current
Update your OpenAPI specification whenever you make changes to the API. Cut a new GitHub release to publish the updated documentation.
Notifying consumers of breaking changes
Inform consumers of breaking changes with sufficient notice. Use the access requests in your producer dashboard to contact affected consumers.
Reviewing access requests promptly
Respond to consumer access requests within 2 working days. Provide a clear reason if rejecting.
Maintaining contact details
Keep the info.contact.email field in your spec pointing to an active team inbox
Deprecation and removal
If you need to remove an API, notify all consumers and the marketplace team at least 30 days in advance
Questions about your listing? Contact the marketplace team or manage your APIs from your producer dashboard.

6. Data governance

As an API producer you are a data controller (or joint data controller) for the data exposed through your API. The following standards apply to all producers listing on the marketplace.

Legal framework

  • UK GDPR and the Data Protection Act 2018 — you must ensure a lawful basis exists for each category of personal data exposed through your API and document it in your API specification
  • Government Security Classifications (GSC) policy — APIs exposing Official-Sensitive data require additional governance controls and must be declared as such in the marketplace
  • Public Records Act 1958 — court records and justice data may carry public record obligations that limit how they can be shared

Data sharing agreements

Before approving consumer access to any API containing personal data you must:

  • Confirm a Data Processing Agreement (DPA) or Data Sharing Agreement (DSA) is in place with the consumer’s organisation
  • Record the legal basis for the data sharing arrangement
  • Confirm the consumer’s use case falls within the scope of the agreement
  • Notify your Data Protection Officer (DPO) of any new data sharing arrangements involving personal data
! WarningDo not approve access to personal data APIs without a signed DPA or DSA in place, regardless of the consumer’s urgency or seniority.

Data classification

Official
Eligible for marketplace listing. Standard data protection controls required. Declare in your OpenAPI spec info block.
Official-Sensitive
Eligible with enhanced governance. Formal DSA required before any access is granted. Consumers must demonstrate enhanced security controls. Longer approval timeline.
Secret / Top Secret
Not eligible for marketplace listing.

Data minimisation

  • Expose only the minimum data fields necessary — do not include fields that no current consumer requires
  • Review exposed data fields when a consumer’s access is revoked
  • Do not expose internal identifiers, system fields or debug data in API responses

Audit and monitoring

  • Log all API calls with sufficient detail to support forensic investigation (timestamp, consumer ID, endpoint, response code)
  • Retain access logs for a minimum of 12 months
  • Make logs available to the marketplace team or HMCTS security team on request
  • Be able to identify which consumers were affected in the event of a data breach

Data breaches

As data controller, you must:

  1. Report any suspected or confirmed breach to the HMCTS DPO within 72 hours (UK GDPR Article 33)
  2. Notify affected consumers as part of your incident response
  3. Have an incident response plan that specifically covers API-related breaches
  4. Preserve logs and evidence for investigation — do not attempt to conceal a breach

Accountability

API Owner (you)
Accountable for the accuracy, security and lawfulness of data exposed through your API
Data Controller
HMCTS — responsible for the overall lawfulness of data processing across the marketplace
DPO
Must be consulted on any new data sharing arrangement involving personal data
Marketplace team
Responsible for onboarding governance, standards enforcement and access audit
Questions about your data governance obligations? Contact the marketplace team or consult your HMCTS Data Protection Officer.

Consumer Guidance

How to find, request and use HMCTS APIs responsibly.

Contents

  1. Before you request access
  2. Making an access request
  3. Using the API responsibly
  4. Error handling and resilience
  5. Keeping access current
  6. Getting help
  7. Data governance

Before you request access

Understand what you need

  • Read the API’s plain-English description and understand what data it returns and what it does not return
  • Check the classification — Official-Sensitive APIs require additional justification and may have longer approval times
  • Confirm your service or use case is within the intended scope of the API. Do not request access speculatively.

Check your organisation is eligible

  • You must be part of HMCTS Digital and Technology Solutions, a justice sector partner, or an approved third party
  • You need a valid work email address to register
  • Your organisation must have a data sharing agreement in place where required — check with the API owner
Not sure if your use case is appropriate? Sign in and raise a question via your consumer dashboard, or contact the marketplace team.

Making an access request

What you’ll need to provide

Use case description
What you are building and why you need this API
Environment
Whether you need sandbox, production, or both
Expected call volume
Low, medium or high — this helps the producer plan capacity
Authentication readiness
Confirmation that your system can implement OAuth 2.0 with JWT bearer tokens

What happens next

  1. The API owner reviews your request within 2 working days
  2. You’ll be notified in your dashboard if approved or rejected
  3. If rejected, a reason will be given and you may resubmit with additional information
  4. Once approved, your credentials will be issued via a secure channel
! WarningDo not attempt to access an API before your request has been approved. Unauthorised access attempts are logged and may affect future requests.

Using the API responsibly

Rate limits and fair use

  • Do not exceed the rate limits defined in the API specification
  • Cache responses where appropriate — do not poll repeatedly for data that does not change frequently
  • Use the sandbox environment for development and testing. Never test against production.

Authentication

  • All APIs use OAuth 2.0 with JWT bearer tokens
  • Tokens expire — implement token refresh correctly and do not hard-code credentials
  • Do not share credentials between services or teams. Each consuming service should have its own client credentials.

Data handling

  • Data returned by HMCTS APIs is subject to GDPR and the Data Protection Act 2018
  • Official-Sensitive data must be handled in accordance with the Government Security Classifications policy
  • Do not store API responses longer than necessary for your use case
  • Do not expose raw API responses to end users without appropriate data processing

Error handling and resilience

HTTP status Meaning What to do
400Bad requestCheck your request parameters against the API spec
401UnauthorisedRefresh your token. Do not loop on auth failures.
403ForbiddenYour credentials do not have access to this resource
404Not foundHandle gracefully — the resource may legitimately not exist
429Too many requestsBack off and retry after the period in the Retry-After header
5xxServer errorImplement exponential backoff. Use circuit breakers in your service.
Do not treat the API as guaranteed to be available. Implement circuit breakers and fallbacks in your service architecture.

Keeping access current

  • If your use case changes significantly, notify the API owner and resubmit your access request with updated details
  • If your service is decommissioned, revoke your credentials and notify the marketplace team
  • Access may be reviewed periodically — you may be asked to re-confirm your use case
  • Keep your contact details up to date in your dashboard so the API owner can reach you if there are breaking changes

Getting help

API-specific questions
Use the API detail page to find the owning team’s contact details
Access request support
Raise a support request via your consumer dashboard
Urgent production issues
Contact the HMCTS DTS service desk
Marketplace feedback
Contact the marketplace team

Data governance

When accessing HMCTS APIs you are interacting with data that may be subject to legal and regulatory obligations. The following standards apply to all consumers.

Legal framework

Your organisation must comply with:

  • UK GDPR and the Data Protection Act 2018 — any personal data returned by HMCTS APIs must be processed lawfully, with a documented legal basis
  • Government Security Classifications (GSC) policy — Official-Sensitive data requires enhanced security controls in your systems
  • Computer Misuse Act 1990 — credentials must not be shared or misused; unauthorised access is a criminal offence

Data sharing agreements

! WarningYou must not access any API containing personal data without a signed Data Processing Agreement (DPA) or Data Sharing Agreement (DSA) in place.
  • Ensure your organisation’s legal team has reviewed and approved the data sharing arrangement before submitting a request
  • Do not use data for purposes beyond those stated in your access request
  • Report any change in use case to the API owner before proceeding

Data classification obligations

Official
Standard data protection controls apply. Handle in accordance with your organisation’s information security policy.
Official-Sensitive
Restricted access. Formal DSA required. Enhanced access controls, audit logging and need-to-know access in your systems. Do not downgrade once received.

Data minimisation and retention

  • Request access only to the APIs and data fields you actually need — do not request access speculatively
  • Do not cache or store API responses beyond the time needed to fulfil the request
  • Define and document a retention period for any data stored locally
  • Delete data when it is no longer required for the stated purpose

Data breaches

If you suspect or confirm a data breach involving marketplace API data:

  1. Report to the HMCTS DPO within 72 hours as required by UK GDPR Article 33
  2. Notify the API owner immediately
  3. Preserve logs and evidence for investigation
  4. Have a process for notifying your own users if personal data you hold is compromised

Cross-border data transfers

API responses must not be routed through or stored in systems outside the UK or EEA without prior written approval from the HMCTS DPO. Any cloud infrastructure used to process API responses must be documented in your organisation’s Record of Processing Activities (ROPA).

Offboarding

  • When your service is decommissioned, revoke credentials and notify the API owner
  • Delete all data derived from the API or return it to the data controller
  • Provide a data deletion certificate to the API owner on request
Questions about your data governance obligations? Contact the marketplace team or speak to your organisation’s Data Protection Officer.

    Find, request and use HMCTS data

    “We don’t build APIs — we connect you to them. Like a library — we don’t write the books, we organise them so you can find and borrow what you need.”

    An API Marketplace is a curated catalogue of APIs from across the organisation and beyond.

    Think of it as an App Store for APIs — one centralised hub where teams can browse what’s available, understand what each API does, and request access to use it.

    The marketplace doesn’t create the APIs, it makes them discoverable, documented, and accessible.

    Browse the catalogue

    Who it's for

    API Consumers

    Teams and developers who need to use an existing API rather than build one from scratch.

    API Marketplace Read docs Request access Track requests

    API Producers

    Teams that build and own APIs and want them discoverable and usable by others.

    Publish APIs Manage access Review requests

    Reviewers

    Marketplace team members responsible for governance and quality standards.

    Review submissions Approve APIs Triage requests

    What the API Marketplace does and doesn't do

    ✓  The API Marketplace does ✗  The API Marketplace does not
    ✓Catalogue and curate APIs across the programme✗Build, own or develop APIs
    ✓Provide a single point of discovery✗Host data or run backend services
    ✓Document what each API does in plain English✗Support the API — that stays with the owner
    ✓Manage access requests and the approval workflow✗Make architectural decisions for API teams
    ✓Enforce naming conventions and data classification standards✗Guarantee uptime or SLAs for listed APIs
    ✓Capture demand signals when consumers need data not yet available✗Replace any team's responsibility for their APIs

    Key benefits

    Stops duplication

    Check whether an API already exists before building one. The catalogue makes invisible work visible.

    Faster integration

    Documentation, specs, mock servers and access requests in one place. Integration time reduces from weeks to days.

    Governance and standards

    The approval workflow ensures only APIs that meet quality and classification standards appear in the catalogue.

    Controlled access

    Formal justifications mean sensitive data is only shared with authorised teams who have stated their use case.

    Visibility for leadership

    Leadership and programme management get a clear picture of the API landscape — what exists, who owns it, and what demand looks like.

    Captures demand signals

    When consumers can't find the data they need, they can request a new API — giving teams visibility of what the organisation actually needs.

    Common misconceptions

    "The marketplace team builds the APIs"

    We list them. Your team builds and owns the API. The catalogue makes it discoverable.

    "If it's in the catalogue, the marketplace team supports it"

    Support stays with the API owner. The catalogue is a directory, not a support desk.

    "It's only for developers"

    Product managers, architects, delivery managers and business analysts should all use it.

    "Listing my API means giving up ownership"

    You remain the owner. Listing makes your API discoverable — nothing more.

                    API Standards

                    Before listing an API on the HMCTS API Marketplace, producers must meet the following standards. Use this checklist to assess your API’s readiness.

                    These standards are based on the HMCTS RESTful API Standards and the AMP Catalogue onboarding process.

                    1. Technical requirements

                    OpenAPI 3.x spec
                    Must exist at src/main/resources/openapi/openapi-spec.yml with info.title, info.description and info.version populated
                    Servers block
                    Must follow https://<repo-name>.net/{version} — no SwaggerHub URLs. Version is stamped automatically from the GitHub release tag.
                    Spectral linting
                    Spec must pass the standard Spectral OAS3 ruleset with no errors
                    GitHub Actions workflow
                    Add .github/workflows/publish-api-docs.yml referencing the amp-catalog shared workflow at @v1
                    Published docs site
                    Swagger UI must be live at https://hmcts.github.io/<repo-name>/ before submitting to the catalogue

                    2. Eligibility

                    ! WarningOnly external APIs may be listed. Internal APIs must not be exposed publicly via GitHub Pages.
                    API type Eligible? Notes
                    External, documentation-only Eligible Spec is world-readable via GitHub Pages
                    External, with mock execution Eligible Try-It disabled; documentation only
                    Internal / developers only Not eligible Must wait for the APIM Developer Portal

                    3. Specification quality

                    Your OpenAPI spec should meet the following quality standards to ensure a good experience for consumers browsing the marketplace:

                    Title
                    Clear, human-readable name (not the repo slug)
                    Description
                    Plain-English summary of what the API does and who it is for — minimum one sentence
                    Contact email
                    A real team inbox (not Nagashankar.Ponnaganti@HMCTS.NET)
                    Endpoint summaries
                    Every operation must have a summary and description
                    Schema definitions
                    All request and response bodies defined as named schemas in components/schemas
                    Security scheme
                    Authentication method declared (e.g. bearerAuth) and applied to all protected operations
                    Error responses
                    400, 401, 404 and 500 responses documented for each operation

                    4. Process

                    1. Ensure your API repo is public on GitHub
                    2. Add the publish-api-docs.yml workflow and raise a PR
                    3. Once merged, trigger the workflow manually or cut a release
                    4. Confirm the Swagger UI site is live at https://hmcts.github.io/<repo-name>/
                    5. Submit via the Publish API form in this dashboard
                    6. The marketplace team will review and approve within 2 working days
